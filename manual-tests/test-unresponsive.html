Unresponsive Page Tests

Blocks the web process main thread so WebKitWebView:is-web-process-responsive flips to false.

How the detection works

WebKit only notices a stuck process while it is waiting on one, so the timer starts when input is sent to the page. Click a button below and then keep moving the pointer over the page — the property flips about 3 seconds into the freeze, not immediately.

Nothing is shown at that point. The dialog appears only when you click the frozen page, on the grounds that a page quietly stuck in the background is not worth interrupting you over. Independently, a page that stays stuck for 60 seconds has its web process ended automatically.

The clock below runs off setInterval, so it stops dead during a freeze and resumes afterwards: a second opinion on when the main thread is actually blocked.

Freeze for 5 seconds

Just past the threshold. Click the page during the freeze and the dialog should appear; it goes away on its own once the loop ends, whether or not you answered it.

Freeze for 30 seconds

Long enough to try "Wait" — the dialog should dismiss and then come back on the next click, since the page is still stuck. Too short to reach the 60-second cutoff.

Freeze forever

An unbounded loop: nothing but ending the web process gets this tab back. "Close Page" should take you to the crash page, which reports WEBKIT_WEB_PROCESS_TERMINATED_BY_API and offers a reload.

Freeze forever, then leave it alone

Same unbounded loop, for testing the automatic cutoff. Click the page once so WebKit notices the freeze, then do not touch it: about 60 seconds later the process should be ended for you and the crash page should appear on its own.

Freeze on a timer

Starts a 20-second freeze three seconds from now, so it begins while the pointer is elsewhere. Useful for checking that a background tab stays quiet until you come back and click it.
